# Техническая спецификация Lerua Zakup — бизнес-данные, Журнал склада и Менеджер API

**Статус:** проект технической спецификации для согласования.  
**Основание:** согласованные требования и ответы на анкеты № 1–11; уточнение пользователя о складах и местах хранения.  
**Область:** локальные справочники, складские данные, Журнал склада, Менеджер API, синхронизация с МойСклад и надёжность хранения.  
**Важно:** этот документ описывает предлагаемую техническую реализацию. Он не разрешает начинать кодирование до согласования пользователем.

## 1. Цели и границы

Lerua Zakup остаётся Android-приложением с приоритетом локальной работы. Отсутствие сети или API-токена не должно блокировать просмотр и работу с уже сохранёнными локальными данными.

Основной маршрут бизнес-операций:

`Экран/бизнес-модуль → Журнал склада → Менеджер API → МойСклад API`

Ответы и результаты проходят обратно через Менеджер API в Журнал и соответствующий бизнес-модуль.

Исключение: проверка соединения для индикатора подключения остаётся служебным запросом Менеджера API с прямой передачей статуса индикатору. Она не должна обходить Менеджер API.

### Входит в проектирование

- единая SQLite-база с логически разделёнными модулями;
- Журнал склада и история событий;
- централизованный Менеджер API, типизированные задачи и очереди;
- локальный каталог товаров и услуг «Актуальные товары»;
- справочники складов, организаций и поставщиков;
- локальные способы оплаты и их связи;
- локальные места хранения внутри складов;
- резервное копирование, восстановление, экспорт и политика очистки;
- интерфейсные точки входа и состояния синхронизации.

### Пока не проектируется как законченная бизнес-функция

- конкретный первый тип складского документа/операции;
- алгоритмы внутреннего распределения товаров по местам хранения;
- остатки с разбивкой по складам;
- автоматическое размещение/перемещение товаров между локальными местами;
- массовая параллельная отправка API-запросов.

Первая практическая интеграция справочника — «Актуальные товары МойСклад» в «Дополнительных действиях». До выбора первой складской операции универсальная модель операций проектируется расширяемой, но формы и бизнес-правила конкретного документа не выдумываются.

## 2. Архитектурные слои

Предлагается разделить приложение на логические слои:

1. **Presentation:** экраны и пользовательские сценарии. Экраны не обращаются к HTTP-клиенту и не выполняют SQL самостоятельно.
2. **Application / Use cases:** сценарии синхронизации справочников, изменения локальных статусов, создания операции, постановки задачи, подтверждения восстановления очереди.
3. **Domain:** сущности, статусы, правила переходов, классификация ошибок и бизнес-инварианты.
4. **Data:** репозитории SQLite, транзакции, DAO, миграции, локальные снимки.
5. **Integration:** Менеджер API, адаптер МойСклад API, обработка страниц, таймаутов и сетевых ошибок.
6. **Operations:** резервное копирование, восстановление, экспорт, диагностика и очистка.

Существующий проект уже использует Flutter и зависимость `sqflite`. Предлагается сохранить текущую платформу и внедрять модули поэтапно, не переписывая существующие календарь, тему, настройки и проверку соединения без необходимости.

### Принцип владения данными

- МойСклад владеет внешними ID, названиями и синхронизируемыми полями внешних сущностей.
- Lerua Zakup владеет локальными статусами актуальности, способами оплаты, локальными местами хранения, связями и историей.
- Синхронизация внешних полей не должна перезаписывать локальные поля.
- Ни одна локальная сущность не должна случайно превращаться в запрос на запись в МойСклад.

## 3. Модель локальной базы данных

Одна SQLite-база. Разделение выполняется таблицами, внешними ключами, репозиториями и границами модулей, а не отдельными файлами БД.

### 3.1. Системные таблицы

- `schema_migrations` — применённые версии схемы.
- `app_settings` — несекретные настройки приложения и интеграции.
- `sync_runs` — история запусков синхронизации справочников: тип, начало, завершение, результат, признак полноты и безопасные диагностические сведения.

Access Token не хранить в SQLite; оставить существующее защищённое хранилище.

### 3.2. Товары

Таблица `products`: внутренний локальный ID; уникальный `moysklad_id`; наименование; тип (обычный товар или услуга); физический остаток `stock`; единица измерения (если отсутствует — «Не указано»); локальный статус актуальности; признак архивности и присутствия в последнем полном каталоге; дата последнего успешного сопоставления; технические метаданные.

Архивные позиции доступны в отдельном экране «Архив». Комплекты и модификации не входят в обычный каталог. При архивировании товара локальный статус сбрасывается в «Нераспределённые». При разархивировании требуется запрос пользователю о новом статусе.

Полное обновление каталога атомарно: получить все страницы, проверить полноту и только затем одной транзакцией применить набор изменений. Любая ошибка страницы отменяет применение всего набора. Старый каталог остаётся доступен. Статус актуальности не отправляется в МойСклад.

### 3.3. Склады и места хранения — разные сущности

Таблица `warehouses` — внешний справочник складов МойСклад: внутренний локальный ID; уникальный внешний `moysklad_id`; название и синхронизируемые поля; признак архивности/активности; дата последнего успешного обновления; признак присутствия в последней полной синхронизации.

Склады загружаются и обновляются через API Менеджером API. Локальная запись сохраняет ID МойСклад для устойчивого сопоставления. Не создавать дубликаты при повторной синхронизации.

Таблица `storage_locations` — локальные места хранения Lerua Zakup: внутренний локальный ID; `warehouse_id` — ссылка на локальную запись склада; название; локальный порядок отображения; даты создания и изменения; локальные признаки активности/архивности при необходимости.

Места хранения создаются, переименовываются и удаляются/архивируются локально. Эти действия не создают API-задач и не обращаются к МойСклад. Место хранения не получает внешний ID МойСклад. Его родительский склад определяется локальной связью, а через склад доступен внешний ID.

Подробная логика распределения товаров по местам хранения остаётся за рамками текущего этапа. Схема должна позволять добавить её позднее без изменения идентичности складов и мест.

### 3.4. Организации, способы оплаты и поставщики

Таблица `organizations`: локальный ID; уникальный `moysklad_id`; название и синхронизируемые поля; признак архивности/активности; дата последнего обновления; присутствие в последней полной синхронизации.

Загружаются все доступные неархивные организации при запуске приложения и вручную по команде пользователя. Локальные связи не теряются при обновлении.

Таблица `payment_methods` — локальный справочник способов оплаты: ID, название, даты создания/изменения. Поддержать создание, переименование и удаление с проверкой связей.

Назначение способа оплаты организации должно обеспечивать ограничения: у организации не более одного назначенного способа оплаты; один способ оплаты не может быть назначен более чем одной организации. Незанятый способ оплаты может существовать в справочнике.

Таблица `suppliers`: локальный ID; уникальный `moysklad_id`; название, телефон и другие синхронизируемые поля; локальный статус «Актуальный» / «Прочие»; дата последнего обновления и метаданные.

Поиск поставщиков начинается после ввода минимум двух символов, ищет по части названия и обращается к МойСклад. Результаты поиска сами по себе не сохраняются. При открытии карточки поставщика запись создаётся/обновляется локально. При повторном поиске синхронизируемые поля уже сохранённого поставщика обновляются по его ID, локальный статус сохраняется.

**Связь поставщика с организацией:** в карточке актуального поставщика пользователь выбирает способ оплаты. Способ оплаты однозначно связан с организацией; по выбранному способу оплаты приложение определяет организацию для будущих API-запросов по операциям с этим поставщиком. Поэтому отдельный выбор организации при каждой операции не требуется в базовом сценарии. Если нужная связка не настроена, показать предупреждение и предложить завершить настройку до продолжения операции.

При создании складской операции сохранить в самой операции ID организации и способ оплаты, действовавшие на тот момент. Изменение назначения в карточке поставщика или организации влияет только на новые операции, не переписывает старые.

### 3.5. Операции и Журнал

Предлагаемые таблицы:

- `business_operations` — локальная операция, её тип, бизнес-статус, поставщик, снимок ID организации и способа оплаты, даты и полезная нагрузка;
- `business_operation_lines` — строки операции, каждая строка отдельна даже при повторном добавлении того же товара;
- `warehouse_journal_entries` — основная запись Журнала;
- `warehouse_journal_events` — неизменяемая история событий/переходов;
- `journal_api_task_links` — связь Журнала и задач Менеджера API с поддержкой 1:N, N:1 и N:M.

Создание подтверждённой пользователем операции и запись Журнала должны выполняться в одной SQLite-транзакции: либо сохраняются обе части, либо ни одна. Автосохранение черновика — отдельный механизм и само по себе не создаёт полноценную запись Журнала.

Журнал фиксирует намерение, результат локального сохранения, постановку в очередь, попытки, ответы и итог. Снимок ключевых полей операции хранится для последующего аудита. Секреты и Access Token исключаются.

Бизнес-статус операции и технический статус API-задачи — разные состояния. Их нельзя смешивать в одном поле.

### 3.6. Менеджер API

Предлагаемые таблицы:

- `api_tasks` — задача, тип/логическая очередь, связанная операция/справочник, уникальный локальный ID, статус, время поступления, число попыток, безопасные параметры запроса;
- `api_task_attempts` — каждая попытка, время начала/окончания, HTTP-результат, классификация ошибки, безопасная диагностическая выдержка;
- `api_task_events` — история переходов;
- `api_queue_state` — приостановка, причина, состояние восстановления и подтверждения пользователя.

Тело запроса/ответа сохранять только в необходимом объёме и после фильтрации секретов. Не журналировать токен, заголовок Authorization и не нужные для диагностики приватные данные.

## 4. Журнал склада

Журнал — долговременная локальная фиксация жизненного цикла складских операций и связанных задач.

Для каждой операции фиксируются: намерение; результат локальной транзакции; постановка связанных задач; переходы состояния; попытки и результаты API; итог операции либо неопределённость; ручные действия пользователя.

В списке показывать краткое состояние. Детальная карточка показывает хронологию, ID операции, ID задачи, безопасные запросы/ответы, попытки и причины ошибок.

Срок хранения записей Журнала настраиваемый, начальное значение — один месяц. Автоочистка разрешена только после успешного создания резервной копии. Если резервная копия не создана, очистка не выполняется. Удаление отдельной записи пользователем требует подтверждения и не должно нарушать ссылочную целостность связанных записей/задач.

## 5. Менеджер API и очередь

### 5.1. Централизация

Все запросы к МойСклад проходят через единый Менеджер API. UI и бизнес-модули не содержат собственных HTTP-вызовов. Использовать официальный JSON API 1.2, HTTPS и Bearer-токен из защищённого хранилища.

### 5.2. Логические очереди и порядок

Логические очереди разделяются по типам бизнес-логики/запросов и расширяются при добавлении модулей. При этом диспетчер один и обрабатывает задачи строго последовательно в общей FIFO-очереди по времени поступления. Несколько логических очередей не означают параллельную отправку.

Параллельность не включать в первой реализации. Вернуться к ней можно только после отдельного анализа зависимостей, лимитов API, идемпотентности и доказательства безопасности.

### 5.3. Состояния задачи

Предлагаемые технические статусы: `pending`, `running`, `retry_wait`, `succeeded`, `failed`, `uncertain`, `cancelled`, `paused`. В интерфейсе показывать понятные русские подписи.

### 5.4. Повторы и ошибки

Для временной ошибки — максимум три попытки всего, включая первоначальную. Для постоянных ошибок автоматические повторы не выполнять. Ошибка одной задачи изолируется и не блокирует остальные задачи. При потере соединения/API все очереди приостанавливаются до восстановления.

Неопределённый результат — отдельное состояние: если запрос мог быть принят МойСклад, но ответ не получен, не отправлять его повторно вслепую. Сначала ручная или безопасная автоматизированная проверка результата.

Интервалы между временными повторами и точная классификация HTTP/сетевых ошибок — технические параметры реализации; они не меняют лимит трёх попыток.

### 5.5. Восстановление после перезапуска и watchdog

После запуска приложения восстановить сохранённые состояния, но не продолжать отправку автоматически. Показать пользователю состояние очередей и запросить подтверждение продолжения.

Если задача находится в `running` более пяти минут, считать её зависшей и инициировать аварийный сценарий. Пять минут — порог обнаружения, а не разрешение автоматически повторить запрос. Сначала проверить возможность установить результат. Если подтвердить принятие/непринятие нельзя, задача переходит в `uncertain`; блокировка очереди снимается безопасно только после фиксации неопределённости и истории.

Предусмотреть ручную аварийную остановку/разблокировку. Она требует подтверждения и записывает событие в Журнал. Нельзя стирать задачу или терять факт возможной отправки.

### 5.6. Идемпотентность

Локальный уникальный ID защищает от повторного создания локальной операции, но сам по себе не гарантирует идемпотентность на стороне МойСклад. Для каждой операции адаптер определяет стратегию: поддерживаемый ключ идемпотентности, проверка результата по внешним данным либо ручная проверка. При отсутствии надёжной стратегии неоднозначный результат блокирует автоматический повтор.

## 6. Синхронизация справочников

Общий принцип: локальные копии доступны офлайн; обновление запускается при старте и по ручной команде в соответствии с правилами справочника. Одновременные одинаковые обновления не запускаются.

- **Товары/услуги:** полная пагинация, атомарное применение, откат при любой ошибке, время последней успешной полной синхронизации.
- **Организации:** все неархивные; локальная копия; автообновление при запуске и ручная команда; локальные связи способов оплаты сохраняются по ID организации.
- **Склады:** запрос через Менеджер API; локальная копия с ID МойСклад; обновление по внешнему ID. Локальные места хранения не входят в API-синхронизацию.
- **Поставщики:** обновление локально сохранённых при запуске; сетевой поиск совпадений при каждом поисковом запросе (от двух символов); сохранение результата после открытия карточки.
- **Места хранения:** локальные CRUD-операции внутри выбранного склада, без API-задач.

Для любого справочника отсутствие сущности во внешнем ответе можно фиксировать только при подтверждённой полной синхронизации соответствующего набора. Частичный ответ/ошибка не должен приводить к массовой пометке сущностей отсутствующими.

## 7. Резервное копирование и восстановление

- Ежедневная автоматическая копия и ручное создание копии.
- Место хранения выбирает пользователь через системный механизм выбора папки.
- Хранить последние 30 успешных ежедневных копий.
- Если папка недоступна или запись не удалась — запросить другое место; не отмечать копию успешной.
- Автоматическая очистка просроченных записей Журнала только после успешной резервной копии.
- При подозрении на повреждение БД остановить операции с данными и запросить решение пользователя; не выполнять автоматический откат без согласия.
- Экспорт CSV/JSON с выбором раздела и периода.
- Резервная копия должна быть согласованной: SQLite backup API/безопасный snapshot, а не простое копирование активного файла во время транзакций.
- Восстановление проверяет целостность копии до замены текущей БД. Оригинальная БД сохраняется до успешной проверки восстановленной копии.

Следует отдельно проверить технические ограничения Android на фоновую ежедневную работу и доступ к пользовательской папке. Если ОС не гарантирует точное время запуска, приложение показывает дату последней успешной копии и выполняет пропущенную проверку при следующем подходящем запуске. Не обещать гарантированный запуск в выключенном/принудительно остановленном приложении.

## 8. Безопасность

- Access Token только в защищённом хранилище.
- Только HTTPS и Bearer Authorization.
- Исключить токен и заголовки авторизации из журналов, диагностик, экспорта и резервных копий.
- Подробные API-запросы/ответы очищать от секретов до сохранения.
- Удаление токена: ожидающие задачи очищаются согласно согласованному правилу; текущая задача безопасно останавливается. Если результат мог быть принят — сохранить `uncertain`, не повторять автоматически. Каталог и Журнал не удалять.
- Сетевые запросы имеют конечные таймауты; зависший процесс не должен бесконечно удерживать диспетчер.

## 9. Интерфейсные модули

- «Дополнительные действия»: «Актуальные товары МойСклад», «Склады и места хранения», «Поставщики», «Организации и способы оплаты». Справочник контрагентов в UI называть «Поставщики».
- «Актуальные товары»: полноэкранный экран, три категории, поиск по названию, фильтр статуса, сортировка, массовое выделение, режим одного товара, отдельный архив, ручное обновление и дата последней полной синхронизации.
- «Склады и места хранения»: список синхронизированных складов; внутри выбранного склада — локальные места хранения. Состояние синхронизации склада показывается отдельно от локального управления местами.
- «Поставщики»: поиск с двух символов; «Актуальные»/«Прочие»; карточка и локальное назначение способа оплаты, связанного с организацией.
- «Организации»: список неархивных организаций, ручное обновление, локальное назначение одного способа оплаты на организацию.
- «Журнал склада»: доступ через настройки, как согласовано.
- «Менеджер API»: управление очередями/задачами из Журнала или его деталей: просмотр, ручной повтор ошибок, отмена ожидающих, пауза/возобновление, аварийное вмешательство и подтверждение восстановления.
- Не показывать полные каталоги в поисковых экранах до ввода запроса, кроме справочников с согласованным отдельным списком.

## 10. Тестируемые инварианты

1. Ни один экран/репозиторий бизнес-модуля не выполняет прямой HTTP-запрос.
2. Один внешний ID МойСклад соответствует не более чем одной локальной записи справочника.
3. Ошибка любой страницы полной синхронизации не меняет действующий локальный каталог.
4. Локальный статус актуальности не перезаписывается синхронизацией.
5. Локальные места хранения не создают API-задач и не отправляются в МойСклад.
6. Обновление склада сопоставляет записи по ID МойСклад и не теряет дочерние локальные места хранения.
7. Создание операции и первичной записи Журнала атомарны.
8. Одна задача не отправляется параллельно сама с собой; общая очередь последовательна.
9. После перезапуска очередь ожидает подтверждения пользователя.
10. Временная ошибка не приводит к более чем трём попыткам всего.
11. Задача старше пяти минут не отправляется автоматически повторно только из-за watchdog.
12. Неопределённый результат не повторяется автоматически.
13. Изменение назначения способа оплаты не изменяет снимки ранее созданных операций.
14. Способ оплаты не назначается нескольким организациям; у организации не более одного способа оплаты.
15. Успешная резервная копия предшествует автоочистке просроченного Журнала.
16. Access Token отсутствует во всех диагностических данных и экспортируемых записях.

## 11. Открытые технические решения

Разработчик должен предложить и проверить, не выдавая эти детали за уже принятые пользовательские решения:

- интервалы между тремя попытками и классификация временных ошибок;
- формат безопасного снимка запроса/ответа;
- механизм проверки результата после сетевого таймаута для каждого типа операции;
- формат резервной копии и UX восстановления;
- ежедневная фоновая задача Android с учётом ограничений ОС;
- поведение при удалении/архивировании склада, у которого есть локальные места хранения;
- правила удаления/архивирования локального места хранения, если оно используется будущими операциями;
- конкретный состав снимка организации/способа оплаты (ID обязателен);
- точная навигация и размещение экранов справочников.

## 12. Критерии готовности к реализации

Перед кодированием пользователь должен согласовать архитектурное разделение Журнал/Менеджер API/справочники, схему SQLite и связи, синхронизацию и сохранение локальных данных, очередь/повторы/неопределённые результаты/watchdog, резервирование и интерфейсную структуру. До подтверждения код не изменять.
