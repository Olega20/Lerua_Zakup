# Реализация бизнес-архитектуры — журнал изменений

**Статус:** реализация начата по прямому подтверждению пользователя от 20.11.2026.

## Подтверждённые проектные предположения

1. В карточке поставщика хранится одно текущее назначение способа оплаты. Несколько поставщиков могут использовать один способ оплаты.
2. Названия мест хранения уникальны в пределах одного склада.

## Обязательное требование к диагностике

Любая ошибка, возникающая в приложении при работе с локальной БД, синхронизацией справочников, Менеджером API, сетью или обработкой ответа МойСклад, должна быть зафиксирована в Журнале склада. Запись должна по возможности содержать:
- компонент и этап выполнения;
- категорию и стабильный технический код ошибки;
- понятное пользователю описание и рекомендуемое действие;
- безопасные технические детали, HTTP-статус и идентификатор связанной задачи/операции;
- время и номер попытки.

Секреты, Access Token, заголовок Authorization и чувствительные данные не сохраняются. Ошибка записи в сам Журнал не должна бесконечно зацикливать приложение: она должна быть передана в отдельный безопасный системный канал диагностики и явно отображена как критическая проблема сохранности журнала. Нельзя молча проглатывать ошибку записи диагностики.

Следующие этапы выполняются отдельными проверяемыми коммитами. Наличие таблицы в схеме не означает, что соответствующий пользовательский сценарий уже реализован.

### Этап 1. Расширение диагностики — начато

- Добавлены структурированные поля диагностической записи: компонент, стабильный код ошибки, рекомендуемое действие, безопасные технические сведения, correlation ID, ID операции/задачи и номер попытки.
- Добавлен классификатор исключений для таймаутов, сетевых ошибок, SQLite, некорректного формата и системных ошибок.
- Ошибки внутри проверки подключения Менеджером API теперь проходят через классификатор и записываются с понятным описанием и рекомендацией.
- Перед сохранением диагностического текста выполняется фильтрация Bearer/Access Token.
- Схема SQLite обновлена до версии 2 с миграцией дополнительных диагностических полей.
- Экран деталей Журнала использует расширенный безопасный текст записи.

**Проверка после расширения диагностики:** `flutter analyze --no-pub` — успешно; `flutter test --no-pub` — 129 тестов пройдены.
**Ограничение текущего состояния:** классификатор уже подключён к проверке соединения, но ещё не все модули приложения направляют свои ошибки через общий репортёр. Это обязательная часть следующих подэтапов, прежде чем считать требование о полноте диагностики выполненным.


### Этап 2. Долговременное хранилище Менеджера API — реализация в GitHub, локальная проверка ожидает подключения ПК

- Добавлена типизированная модель API-задачи и состояний.
- Реализовано создание задач с устойчивым UID и защитой от повторного локального добавления.
- Задачи получают глобальный FIFO-порядок независимо от логической очереди.
- Атомарное получение следующей задачи создаёт запись попытки до сетевого вызова.
- Реализованы сохранение результата попытки, безопасного ответа и события перехода состояния.
- Реализованы пауза отдельной логической очереди и глобальная пауза всех очередей.
- Watchdog переводит задачу, зависшую в состоянии отправки более пяти минут, в неопределённое состояние; автоматический повтор не выполняется.\n- После перезапуска незавершённые задачи переводятся в неопределённое состояние, все очереди глобально блокируются до явного подтверждения пользователя; ранее установленные ручные паузы отдельных очередей сохраняются.
- После третьей временной ошибки задача становится окончательно ошибочной и больше не попадает в выборку на отправку.
- Перед сохранением JSON рекурсивно удаляются поля токена, авторизации, пароля и секрета.
- Добавлены тесты на идемпотентное добавление, FIFO, паузу, очистку секретов, watchdog и предел трёх попыток.

**Проверка:** файлы и коммит проверены через GitHub API. Локальные `flutter analyze` и `flutter test` пока не выполнены: компьютер разработки был отключён. Этот этап не объявляется прошедшим тестирование; после подключения ПК обязательны синхронизация, анализ и запуск полного набора тестов.


### Дополнительная корректировка этапа 2 — 20.11.2026

- Глобальная пауза хранится отдельным флагом `__all__` и не перезаписывает ручные паузы логических очередей.
- Глобальное снятие паузы не снимает блокировку подтверждения после перезапуска; диспетчер учитывает оба блокирующих флага.
- Подтверждение после перезапуска требуется только при наличии незавершённых задач. Запущенные запросы переводятся в неопределённое состояние, ожидающие остаются на месте.
- Исправлена ошибка компиляции в watchdog: счётчик изменённых задач объявлен внутри транзакции.
- Исправлено ограничение безопасного диагностического текста: длина обрезается после фильтрации секретов.
- Добавлены регрессионные тесты для сохранения ручной паузы и восстановления пустой очереди.
- Тесты добавлены, но локально не запускались из-за недоступности компьютера.


### Пакетная реализация согласованных разделов — 20.11.2026

**Реализовано в локальной рабочей копии, проверено тестами; готовится релизная сборка.**

- Менеджер API: постоянная FIFO-очередь, один последовательный исполнитель GET-запросов, история попыток, три попытки временных ошибок, ручной повтор окончательно ошибочных задач, ручное разрешение неопределённого результата, паузы логических очередей и глобальная пауза. Временные паузы сети/сервиса не должны снимать ручную паузу пользователя.
- Журнал склада: события создания намерения и локального сохранения операции, статусы, история событий и связь с API-задачами. Ошибки API-задач фиксируются в той же транзакции SQLite; при невозможности записи используется аварийный диагностический канал.
- Каталог МойСклад: товары и услуги, отдельный архив, остатки и единицы измерения, локальные статусы актуальности, поиск, фильтр, массовая разметка и последовательный режим проверки. Изменения каталога применяются только после полного успешного получения всех страниц.
- Склады МойСклад и локальные места хранения: локальные ID складов МойСклад, места хранения создаются внутри склада и не отправляются в API.
- Организации МойСклад, локальные способы оплаты и поставщики: локальные связи и статусы, поиск поставщиков по двум и более символам, обновление сохранённой карточки по внешнему ID.
- Бизнес-операции: единый локальный черновик, снимки реквизитов организации/способа оплаты/поставщика, атомарное создание подготовленной операции и записи Журнала. Конкретный тип первой операции пока не реализуется — он не был выбран в требованиях.
- Резервное копирование: выбор папки, ежедневные и ручные копии, ротация до 30 последних копий, проверка целостности перед восстановлением, экспорт CSV/JSON и настраиваемый срок хранения Журнала (по умолчанию 30 дней). Удаление старых данных выполняется только после успешного создания копии.
- Интерфейсы разделов добавлены в «Прочие действия».

**Границы текущей реализации:** исполнитель Менеджера API пока намеренно принимает только GET-запросы. Создание/изменение документов МойСклад не включается до выбора конкретного типа бизнес-операции и отдельной реализации безопасной обработки неоднозначных результатов записи. Реальное соединение с аккаунтом МойСклад и проверка данных на устройстве выполняются при пользовательском тестировании после установки.

**Проверки на ПК:** flutter analyze — без замечаний; flutter test — все 150 тестов пройдены. Отдельно повторно пройдены тесты очереди API и резервного копирования. После этих проверок исправлены найденные ошибки маскирования секретов, фабрики SQLite при проверке резервной копии и сохранения ручной паузы. Release APK собирается отдельно.
