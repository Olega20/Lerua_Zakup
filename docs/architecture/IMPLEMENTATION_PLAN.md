# План реализации Lerua Zakup — справочники, Журнал склада и Менеджер API

**Статус:** проект плана для согласования; кодирование не начинать до подтверждения.  
**Базовая ветка:** `main`.  
**Подход:** небольшие проверяемые этапы, отдельный коммит каждого завершённого этапа, локальные тесты на ПК, без GitHub Actions.

## Принципы выполнения

- Не ломать работающие календарь, настройки, тему, защищённое хранение токена и монитор подключения.
- Перед каждым этапом фиксировать затрагиваемые модули и критерии приёмки.
- Реализовывать вертикальными срезами: схема → репозитории → сценарии → UI → тесты.
- Все исходники и документацию изменять через GitHub API; затем синхронизировать ПК с `origin/main`, запускать проверки и сверять результат.
- Никаких прямых API-вызовов из UI или отдельных бизнес-модулей.
- Никакой параллельной отправки в первой версии.
- Не реализовывать конкретный складской документ, пока пользователь не выберет первую операцию.
- Не включать локальные места хранения в API-синхронизацию.

## Этап 0. Согласование и технический дизайн

**Результат:** утверждённые спецификация, план, ER-диаграмма и контракты модулей.

1. Согласовать техническую спецификацию.
2. Уточнить технические решения по SQLite, watchdog, резервированию и безопасному восстановлению.
3. Подготовить ER-диаграмму с внешними ID и локальными связями.
4. Подготовить диаграммы состояний бизнес-операции и API-задачи отдельно.
5. Определить контракты репозиториев, API-клиента, Менеджера API и Журнала.
6. Зафиксировать тестовую матрицу.

**Приёмка:** нет неразрешённых противоречий в бизнес-правилах; пользователь явно подтвердил переход к реализации.

## Этап 1. Основа локальной базы

1. Проверить текущий слой `lib/core/storage` и использование SQLite.
2. Добавить версионируемые миграции и единый DatabaseProvider.
3. Создать таблицы системных настроек и запусков синхронизации.
4. Добавить репозитории и транзакционные тесты.
5. Реализовать безопасную обработку ошибки открытия/целостности БД без автоматического уничтожения данных.

**Приёмка:** миграции проходят с чистой БД и с предыдущей версией; повторный запуск миграций безопасен; ошибка БД не приводит к очистке данных.

## Этап 2. Инфраструктура Менеджера API

1. Выделить единый MoySkladApiClient с авторизацией, таймаутами, gzip/JSON и централизованной обработкой ошибок.
2. Сохранить существующий способ хранения токена и проверку подключения, перенаправив сетевую работу через единый слой.
3. Создать хранилище задач, попыток и событий.
4. Реализовать общую FIFO-очередь с одним исполнителем.
5. Реализовать статусы, классификатор временных/постоянных ошибок, лимит трёх попыток.
6. Реализовать паузу всех очередей при недоступности соединения/API.
7. Реализовать восстановление после перезапуска только после подтверждения пользователя.
8. Реализовать watchdog пяти минут и переход в безопасное неопределённое состояние без слепого повтора.
9. Реализовать ручные действия: повтор допустимых ошибок, отмена ожидающих, пауза/возобновление, аварийная остановка.

**Приёмка:** тесты доказывают FIFO, отсутствие двойной отправки, максимум три попытки, безопасное восстановление, остановку при потере связи и отсутствие повтора неопределённой задачи.

## Этап 3. Журнал склада

1. Создать записи Журнала, события и гибкие связи с API-задачами.
2. Реализовать транзакционное создание намерения и результата локального сохранения.
3. Реализовать хронологию, детали и безопасное отображение диагностики.
4. Связать результаты Менеджера API с записями Журнала.
5. Добавить UI Журнала в настройках.
6. Добавить действия по задачам из карточки Журнала.

**Приёмка:** сбой транзакции не оставляет сиротскую операцию или запись; связи 1:N/N:1/N:M проверены; токен не появляется в журнале.

## Этап 4. Справочник «Актуальные товары МойСклад»

1. Создать локальную модель товара и репозиторий.
2. Реализовать постраничную загрузку через Менеджер API.
3. Проверять полноту загрузки и атомарно применять весь каталог.
4. Сопоставлять по ID МойСклад, не теряя локальный статус.
5. Реализовать архив, отсутствие в текущем каталоге и восстановление прежнего статуса.
6. Реализовать список с тремя категориями, поиск, фильтр, сортировку и счётчики.
7. Реализовать массовое выделение с подтверждением.
8. Реализовать просмотр по одному товару с кнопками «Назад»/«Вперёд».
9. Добавить ручное обновление и дату последней полной синхронизации.
10. Подключить раздел в «Дополнительные действия».

**Приёмка:** офлайн-каталог работает; ошибка любой страницы не меняет локальные данные; повторная синхронизация не дублирует товары; локальные статусы не теряются.

## Этап 5. Справочник складов и локальные места хранения

1. Создать таблицу складов с уникальным ID МойСклад.
2. Реализовать запрос и обновление складов через Менеджер API.
3. Сохранять локальные записи и обновлять по внешнему ID.
4. Создать локальную таблицу мест хранения с FK на локальный склад.
5. Реализовать локальное создание, переименование, сортировку и удаление/архивирование мест.
6. Реализовать экран складов и вложенный список локальных мест хранения.

**Критически важно:** запрос/обновление складов — API-задачи; создание/изменение/удаление мест хранения — локальные операции без API-задач. Обновление списка складов не должно стирать локальные места хранения.

**Приёмка:** повторная синхронизация складов не создаёт дубликаты и не теряет места хранения; CRUD мест хранения работает офлайн; локальные действия с местами не создают сетевых задач.

## Этап 6. Организации и способы оплаты

1. Создать локальный справочник организаций с внешними ID.
2. Реализовать загрузку всех неархивных организаций при запуске и вручную.
3. Создать локальный справочник способов оплаты.
4. Реализовать создание, переименование и удаление способов оплаты.
5. Обеспечить ограничения: один способ оплаты — максимум одной организации; у организации — максимум один способ оплаты.
6. Сохранять локальные назначения при обновлении организаций.
7. Реализовать UI справочника организаций и настройки способа оплаты.

**Приёмка:** синхронизация не сбрасывает назначения; ограничения проверяются БД и бизнес-слоем; архивные организации не попадают в рабочий список.

## Этап 7. Поставщики

1. Создать локальную модель поставщика и статусы «Актуальный»/«Прочие».
2. Реализовать обновление сохранённых поставщиков при запуске.
3. Реализовать сетевой поиск от двух символов по части названия через Менеджер API.
4. Сохранять поставщика только после открытия карточки.
5. Обновлять синхронизируемые поля по ID, не затрагивая локальный статус.
6. В карточке актуального поставщика реализовать выбор способа оплаты.
7. Определять организацию через выбранный способ оплаты.
8. При отсутствии настройки показывать предупреждение и вести к её назначению.

**Приёмка:** поиск не загружает полный каталог; неоткрытые результаты не сохраняются; локальные статусы переживают синхронизацию; назначение оплаты однозначно разрешает организацию.

## Этап 8. Снимки реквизитов в складских операциях

Пока не создавать конкретный тип документа. Подготовить общий механизм:
1. Сохранение ID поставщика, организации и способа оплаты в локальной операции.
2. Снимок реквизитов на момент создания операции.
3. Защита исторических значений от изменения при обновлении карточек справочников.
4. Связь операции с Журналом и API-задачами.

**Приёмка:** изменение способа оплаты после создания тестовой операции не меняет её реквизиты; транзакция операции и Журнала атомарна.

## Этап 9. Резервное копирование, восстановление и экспорт

1. Выбор пользовательской папки через Android Storage Access Framework.
2. Безопасное создание SQLite snapshot.
3. Автоматическая ежедневная попытка с учётом ограничений Android и ручная копия.
4. Ротация последних 30 успешных ежедневных копий.
5. Проверка целостности копии и безопасный сценарий восстановления.
6. Экспорт CSV/JSON с выбором раздела и периода.
7. Очистка просроченного Журнала только после успешной копии.
8. UI последней успешной копии и ошибки доступа к папке.

**Приёмка:** неудачная копия не запускает очистку; восстановление не уничтожает текущую БД до проверки копии; сохраняется 30 последних успешных ежедневных копий.

## Этап 10. Сквозная проверка и подготовка релиза

Проверить холодный запуск, отсутствие/невалидность токена, отсутствие интернета, восстановление связи, синхронизацию справочников, офлайн-работу, атомарность каталога, очередь, перезапуск, watchdog, неопределённый результат, Журнал, резервирование, восстановление, отсутствие утечки токена и миграцию с установленной версии.

После успешных проверок — согласовать выпуск, собрать Release APK, проверить установку/запуск и предоставить APK и контрольную сумму.

## Порядок коммитов

Каждый этап или логически завершённый подэтап — отдельный коммит в `main` через GitHub API. После каждого коммита:
1. проверить новый HEAD и содержимое изменённых файлов через GitHub;
2. синхронизировать локальный ПК с `origin/main`;
3. выполнить соответствующие unit/widget/integration тесты;
4. зафиксировать результаты проверки в отчёте этапа.

GitHub Actions не использовать. Не заявлять об успешном тестировании, сборке или установке без фактического подтверждения.

## Что не входит в текущую последовательность

- выбор и реализация первой складской операции;
- распределение товаров по локальным местам хранения;
- складские остатки с разбивкой по отдельным складам;
- синхронизация локальных мест хранения с внешними системами.

Эти задачи будут вынесены в отдельное согласование после готовности справочников и базовой инфраструктуры.
