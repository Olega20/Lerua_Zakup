# Product requirements log

This file stores decisions confirmed by the product owner. Each questionnaire batch is appended with the date, original question, answer, and resulting implementation decision.

## Confirmed decisions before questionnaire

- Show every inventory document available in MoySklad in the inventory section.
- Fetch remote MoySklad inventories and their positions on demand; do not permanently store their remote data in the app's local database.
- Allow editing inventory records/positions in MoySklad.
- Record local inventory draft creation/deletion, submission, remote edits, and failures in the warehouse journal as a chronological event history.
- Keep unsent local drafts on-device for offline continuation.

2. **Несколько складов:** A — полностью проходить товары для первого склада, затем переходить к следующему.
3. **Места хранения:** C — при создании выбирать склады; места хранения не ограничивать.
4. **Отображение остатка:** A — показывать общий остаток по выбранному складу.
5. **Количество закупки/заказа:** A — вводить дополнительное количество к приобретению; текущий остаток показывать для справки.
6. **Товар без поставщика:** B — создавать отдельную запись «Без поставщика».
7. **Товар с несколькими флажками:** A — создавать независимые операции каждого отмеченного типа.
8. **Группировка мест хранения:** A — одна запись поставщика на склад, места хранения перечислять внутри неё.
9. **Незавершённое внесение:** A — сохранять черновик и позволять продолжить позже.
10. **Нумерация:** A — автоматический сквозной номер отдельно для каждого типа операций.

### Следствия для реализации

- Отбор товаров производится по флажку типа операции, а не по наличию остатка.
- Сессия внесения проходит склад за складом; внутри склада учитываются все его места хранения без отдельного фильтра.
- Количество вводится как дополнительное к закупке/заказу, не как целевой остаток.
- Отсутствующий поставщик не блокирует внесение: его позиции группируются в отдельную запись «Без поставщика».
- Если товар отмечен несколькими типами, соответствующие типы обрабатываются независимо.
- Группировка календарных документов — по типу операции, складу и поставщику; места хранения не создают отдельные документы.
- Незавершённая сессия должна быть восстанавливаемым локальным черновиком.
- Номер генерируется независимо в пределах каждого типа операций.

## Раунд 2 — закупка, заказ и перемещение

Дата фиксации: 2026-11-26

1. **Перемещение между складами:** A — выбрать склад-источник и склад-получатель; количество списывается с первого и приходуется на второй.
2. **Отбор товаров для перемещения:** B — включать товары с флажком «Перемещение» и разрешить вручную добавлять другие товары.
3. **Дата перемещения в календаре:** A — текущая дата.
4. **Группировка календарных записей:** A — отдельная запись на каждый склад и поставщика в рамках типа операции.
5. **Список старых операций:** A — показывать дату, номер, склад и поставщика.
6. **Действия с созданной записью:** B — просмотр и удаление всей записи; редактирование содержимого пока не требуется.
7. **Создание календарных записей:** A — сразу после нажатия «Завершить».
8. **Склад без введённых количеств:** A — не создавать для него запись.
9. **Порядок товаров:** пользовательский вариант — сортировать сначала по порядку мест хранения (в том порядке, в котором они расположены в системе), затем внутри каждого места хранения по алфавиту.
10. **Снимок данных товара:** A — сохранять сведения о товаре на момент создания операции.

### Следствия для реализации

- Перемещение должно иметь два склада: источник и получатель; после подтверждённого завершения требуется отразить расход на источнике и приход на получателе. Нужны проверки, исключающие совпадение складов и отрицательный остаток/недостаточное количество на источнике (точные правила ещё уточнить).
- В перемещение автоматически попадают товары с соответствующим флажком, но пользователь может вручную добавить иные товары.
- Дата записи перемещения — дата завершения, текущий день.
- Группировка календаря остаётся раздельной по типу операции, складу и поставщику.
- В списке операций показываются только дата, номер, склад и поставщик; количество позиций и сумма не обязательны.
- Существующую запись можно открыть для просмотра или удалить целиком; частичное редактирование не входит в текущий объём.
- Записи календаря создаются синхронно с командой завершения пользовательского сценария, после подтверждения действия; пустые складские группы пропускаются.
- Сортировка товаров учитывает порядок мест хранения, заданный в МойСклад, а внутри места — алфавитное имя товара.
- В строках операции необходимо хранить неизменяемый снимок существенных атрибутов товара на момент создания, чтобы последующие изменения справочника не переписывали историю.

## Раунд 3 — закупка, заказ и перемещение

Дата фиксации: 2026-11-26

1. **Отражение перемещения в МойСклад:** B — на данном этапе создавать только календарные записи приложения, без создания документа перемещения в МойСклад.
2. **Недостаточный остаток на складе-источнике:** C — допускается перемещение с отрицательным остатком (ответ зафиксирован как правило на будущее; сейчас перемещение остаётся календарной записью без изменения остатков).
3. **Место хранения на складе-получателе:** C — приложение автоматически подбирает место хранения.
4. **Расположение товара:** пользовательское уточнение — каждый товар может находиться только в одном месте хранения; не требуется выбирать место списания среди нескольких мест.
5. **Ручное добавление товаров в перемещение:** A — разрешить добавлять любые актуальные товары.
6. **Удаление созданного перемещения:** вариант не выбран; решение отложено.
7. **Состав снимка товара:** пользовательский вариант — сохранять название, единицу измерения и поставщика.
8. **Изменение позиций черновика:** A — до завершения разрешить удалять позиции и менять количество.
9. **Ошибка при завершении:** C — сохранить черновик и предложить повторить завершение позже.
10. **Результат завершения:** B — показывать только сообщение об успешном завершении, без подробной сводки.

### Следствия для реализации

- На текущем этапе перемещение не создаёт документ в МойСклад и не меняет складские остатки; результатом являются только локальные календарные записи. Необходимо явно отделять это от возможного будущего полноценного проведения перемещения.
- Ответ о разрешении отрицательного остатка относится к будущей логике фактического перемещения и пока не должен приводить к изменению остатков.
- Для будущего фактического перемещения место хранения получателя подбирается автоматически; пользователь уточнил, что товар размещён только в одном месте хранения.
- Ручное добавление в перемещение ограничено актуальными товарами, но не требует флажка «Перемещение».
- Правило удаления уже созданного перемещения остаётся нерешённым; до уточнения нельзя предполагать автоматическую отмену или обратное движение остатков.
- Снимок товара должен включать название, единицу измерения и поставщика; прочие атрибуты не следует добавлять как обязательные без отдельного решения.
- В черновике пользователь может менять количество и удалять позиции до завершения.
- При ошибке финального сохранения данные остаются в черновике; повторное завершение должно быть безопасным и не создавать дубликаты уже сохранённых календарных записей.
- После успешного завершения достаточно короткого подтверждения без сводки.

## Раунд 4 — закупка, заказ и перемещение

Дата фиксации: 2026-11-26

1. **Представление операции в календаре:** пользовательский вариант — показывать поставщика отдельным заголовком, а под ним списком его товары; затем следующий поставщик и его товары. Структура примера:
   - Поставщик
     - Товар
     - Товар
   - Поставщик
     - Товар
     - Товар
2. **Содержимое карточки/записи:** C — показывать товары, количество, единицу измерения и текущий остаток.
3. **Формат номера:** C — тип операции, год и последовательный номер (например, З-2026-0001).
4. **Точность количества:** C — допустимая точность определяется единицей измерения товара.
5. **Отрицательное количество и остаток:** пользовательское уточнение — отрицательное количество закупки вводить нельзя; при этом сам складской остаток может оставаться отрицательным. Это не означает автоматического запрета отображать или учитывать отрицательный текущий остаток.
6. **Сохранение черновика:** B — сохранять изменения при переходе к следующему товару.
7. **Количество черновиков:** пользовательский вариант — разрешить несколько черновиков одного типа операции, с возможностью удалять черновики.
8. **Снятие флажка у товара в черновике:** A — оставить товар в уже созданном черновике без изменений.
9. **Место хранения при автоматическом выборе:** A — использовать единственное место хранения товара в выбранном складе.
10. **Срок жизни черновика:** пользовательский вариант — автоматически удалять черновики через неделю; также разрешить ручное удаление.

### Следствия для реализации

- В календаре операции должны визуально группировать строки по поставщикам: заголовок поставщика, под ним товары; далее следующий поставщик. Сохраняется согласованная ранее группировка по типу операции и складу.
- Внутри подробного представления показывать товар, введённое количество, единицу измерения и текущий остаток.
- Формировать номер с префиксом типа, годом и последовательностью, например З-2026-0001; ранее согласованная независимая нумерация по типам сохраняется.
- Ввод количества должен учитывать точность, допустимую для единицы измерения; отрицательное количество закупки/заказа не разрешать. Отрицательный складской остаток сам по себе допустим и должен корректно отображаться.
- Сохранять черновик при переходе к следующему товару, а не требовать отдельного нажатия сохранения после каждого изменения.
- Разрешить несколько черновиков каждого типа и обеспечить отдельное ручное удаление черновика.
- Изменение флажков товара в справочнике после включения товара в черновик не должно автоматически удалять этот товар из черновика.
- Для автоматического выбора места хранения использовать единственное место хранения товара в выбранном складе; если его нет, требуется определить поведение в следующем раунде.
- Добавить срок жизни черновика: автоматическое удаление через 7 дней и ручное удаление. Для корректной реализации необходимо определить, от какого момента считать неделю, и предупреждать ли пользователя перед автоматическим удалением.

## Раунд 5 — закупка, заказ и перемещение

Дата фиксации: 2026-11-26

1. **Отсчёт срока жизни черновика:** A — неделя отсчитывается с момента создания черновика.
2. **Предупреждение об удалении:** A — не предупреждать; по истечении срока удалять автоматически.
3. **Удаление просроченных черновиков:** A — удалять при следующем запуске приложения, если срок уже истёк.
4. **Отсутствующее место хранения:** пользовательское уточнение — такая ситуация невозможна в нормальном сценарии: после выбора склада показываются только товары, хранящиеся на этом складе/в его местах хранения. Посторонний товар в список попасть не должен.
5. **Остаток в завершённой операции:** B — показывать остаток на момент создания операции.
6. **Удаление завершённой операции:** пользовательское уточнение — пока операции существуют только в календаре приложения и ничего не создаётся в МойСклад; удаление касается календарной записи приложения.
7. **Подтверждение удаления:** A — перед удалением завершённой операции показывать подтверждение с предупреждением о необратимости.
8. **Список черновиков и операций:** пользовательское уточнение — отдельные разделы по типам: «Закупки», «Заказы», «Перемещения»; в списке показывать дату и номер.
9. **Комментарий к операции:** C — комментарии пока не нужны.
10. **Цена:** C — на данном этапе учитывать только количества, без цены и расчёта суммы.

### Следствия для реализации

- Срок автоматического удаления черновика — 7 дней от даты его создания, а не от последнего изменения или открытия.
- Не показывать предупреждения перед истечением срока; просроченные черновики удалять при следующем запуске приложения.
- Список товаров формировать строго в контексте выбранного склада: показывать только товары, фактически относящиеся к выбранному складу и его местам хранения. Отсутствие места хранения для такого товара считается нарушением исходных данных/ошибкой, а не штатным сценарием назначения вручную.
- В завершённой операции показывать зафиксированный остаток на момент создания, а не текущий динамический остаток.
- Удаление завершённой операции удаляет запись только из календаря приложения; никаких запросов на отмену или удаление в МойСклад не отправлять. Перед удалением обязательно подтверждение с предупреждением о необратимости.
- Разделить списки по типам операций: «Закупки», «Заказы», «Перемещения». В каждой строке списка показывать дату и номер; дополнительные поля пока не требуются.
- Не добавлять поля комментариев к операции или товарным позициям.
- Не вводить цены и денежные итоги; текущая версия работает с количествами.
