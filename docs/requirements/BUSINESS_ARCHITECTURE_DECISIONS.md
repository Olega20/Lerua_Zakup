# Согласование бизнес-архитектуры Lerua Zakup

Документ фиксирует ответы пользователя для подготовки спецификации и плана реализации. Предложения разработчика не считаются согласованными, пока пользователь их явно не подтвердил.

## Пакет вопросов № 1 — локальный справочник «Актуальные товары МойСклад»

### Зафиксированные ответы

1. **Назначение и размещение:** раздел «Актуальные товары» открывается отдельным полноэкранным окном из «Дополнительных действий».
2. **Локальная копия:** товары загружаются из МойСклад и сохраняются локально в приложении. Дальнейшая работа с ними должна опираться на локальные записи.
3. **Идентификация:** у каждой локальной записи сохраняется уникальный ID, присвоенный МойСклад. Он используется для сопоставления товара при обновлениях и для связи операций с исходным товаром.
4. **Данные товара:** на первом этапе нужны наименование, общий остаток без разбивки по складам и единица измерения. Разбивка остатков по складам относится к следующему этапу.
5. **Обновление:** справочник должен самообновляться; сопоставление выполняется по уникальному ID МойСклад.
6. **Режимы:** предусмотрены два режима — список и просмотр по одному товару.
7. **Режим списка:** весь каталог показывается в трёх сворачиваемых категориях: «Нераспределённые», «Актуальные», «Не актуальные».
8. **Статусы:** новый товар без назначенного статуса находится в «Нераспределённых». Пользователь может назначить ему «Актуально» или «Не актуально».
9. **Групповое назначение:** в режиме списка можно выделять товары долгим нажатием и менять статус сразу у выбранных товаров.
10. **Режим одного товара:** товары показываются последовательно, по одному на экран; доступны действия «Актуально», «Не актуально», «Назад» и «Вперёд».
11. **Область хранения статуса:** статус актуальности хранится только в Lerua Zakup и никогда не записывается в МойСклад.
12. **Разделение данных:** сведения товара синхронизируются из МойСклад, а статус актуальности и связанные локальные сведения принадлежат Lerua Zakup.
13. **Отсутствие в каталоге:** товар помечается как отсутствующий в текущем каталоге только после успешного обновления справочника, в результате которого товар не обнаружен. Отсутствие интернета или неудачная/неполная попытка обновления не являются основанием для такой отметки.
14. **История:** локальную запись и статус не следует удалять только из-за отсутствия товара в очередном успешно обновлённом каталоге; товар получает признак отсутствия в текущем каталоге.

### Ответы на анкету № 1 — состав и обновление каталога

1. **Состав каталога:** загружать только неархивные товары и услуги.
2. **Типы позиций:** выбрано «только обычные товары». Требуется уточнить, входят ли услуги, явно выбранные в пункте 1, если под обычными товарами подразумеваются только сущности товара.
3. **Остаток:** показывать физический остаток (stock).
4. **Нет единицы измерения:** показывать «Не указано».
5. **Автообновление:** запускать обновление при каждом запуске приложения.
6. **Ручное обновление:** отдельная кнопка обязательна.
7. **Частичное/ошибочное обновление:** сохранить уже загруженные данные, показать предупреждение и предложить повторить обновление. При этом частичное обновление не считается полным успешным обновлением и не может приводить к пометке не найденных в частичной выборке товаров как отсутствующих.
8. **Повторное появление:** если ранее отсутствовавший товар снова появился, восстановить его прежний локальный статус актуальности.
9. **Инструменты списка:** поиск, сортировка и фильтр по статусу.
10. **Порядок режима одного товара:** сначала нераспределённые, затем актуальные, затем неактуальные.

### Открытые вопросы

Следующие детали требуют отдельного согласования в пакетах вопросов. Нельзя считать их решёнными на основании предположений:
- поведение повторного разархивирования ранее архивного товара;
- технические критерии полноты загрузки всех страниц и политика повторов при временных ошибках API;
- поведение навигации «Назад»/«Вперёд» на границах последовательности;
- технические детали расписания автообновления при каждом запуске;
- технические детали локального хранения, резервирования и восстановления;
- взаимодействие операций, Журнала склада и Менеджера API.

### Ответы на анкету № 2 — локальная копия и процесс обновления

1. **Первое открытие при пустом локальном каталоге:** показывать пустой список с кнопкой обновления.
2. **Открытие при наличии локальной копии и идущем обновлении:** сразу показывать старые данные, обновление выполнять в фоне.
3. **Работа без интернета:** разрешить полноценную работу с последней локальной копией.
4. **Повторный запрос обновления во время текущего:** не запускать второе обновление; сообщить, что обновление уже выполняется.
5. **Индикация процесса:** показывать процент выполнения, только если API позволяет достоверно определить прогресс.
6. **Прерывание закрытием приложения:** при следующем запуске начать обновление заново, сохранив локальный каталог.
7. **Применение частичных данных:** сразу обновлять соответствующие локальные товары по мере получения данных.
8. **Ошибки отдельных страниц/записей:** пользователь выбрал считать обновление успешным и помечать не найденные позиции отсутствующими. Это решение противоречит ранее зафиксированному требованию о том, что частичная/неполная загрузка не может служить основанием для отметки товаров отсутствующими. До отдельного уточнения нельзя реализовывать автоматическую пометку отсутствия на основании неполного результата; конфликт вынесен в открытые вопросы.
9. **Время обновления:** показывать дату и время последнего успешного полного обновления в шапке каталога.
10. **Нет токена или токен не работает при наличии локального каталога:** открывать локальный каталог и сообщать, что обновление недоступно.

### Уточнение, требующее согласования

- **Критерий успешности обновления:** первоначальный ответ № 2.8 уточнён ответом № 3.1. Любая ошибка страницы означает неудачное обновление; частичный набор не применяется и не может служить основанием для пометки товаров отсутствующими.

### Ответы на анкету № 3 — состав каталога, поиск и управление статусами

1. **Ошибка хотя бы на одной странице при обновлении:** считать обновление неудачным и не применять полученные данные.
2. **Ошибка после получения части товаров:** откатить все изменения к состоянию до начала обновления. В сочетании с ответом № 3.1 это означает атомарное обновление: сначала получить и проверить полный набор данных, затем применить его; при неудаче локальный каталог остаётся неизменным.
3. **Типы позиций:** включать обычные товары и услуги.
4. **Комплекты и модификации:** не включать ни комплекты, ни модификации.
5. **Архивные товары:** загружать отдельно, но не показывать в обычном списке.
6. **Сортировка по умолчанию:** сначала товары без статуса, затем остальные; внутри категорий — по наименованию.
7. **Поиск:** только по наименованию.
8. **Фильтры:** только по статусу актуальности.
9. **Счётчики:** показывать количество рядом с названием каждой категории.
10. **Массовое изменение статуса:** перед выполнением показывать подтверждение с количеством выбранных товаров.

### Уточнения и приоритет решений

- Ответы № 3.1 и № 3.2 уточняют и заменяют более ранний вариант из ответа № 2.7 о немедленном обновлении локальных записей по мере получения данных. Данные нового каталога не применяются до завершения успешной загрузки; при ошибке изменения не фиксируются.
- Ответ № 3.1 также разрешает противоречие по ответу № 2.8: ошибка хотя бы одной страницы означает неудачное обновление, поэтому неполный результат не может использоваться для пометки товаров отсутствующими. Такая пометка возможна только после успешного получения полного набора.
- Ответы № 3.3 и № 3.4 уточняют ранее неоднозначное указание «только обычные товары»: в каталог входят обычные товары и услуги, комплекты и модификации исключены.


### Ответы на анкету № 4 — просмотр одного товара и архивные позиции

1. **Открытие режима одного товара:** по нажатию на товар в списке.
2. **После назначения статуса в режиме одного товара:** автоматически переходить к следующему товару.
3. **Подтверждение назначения статуса одному товару:** не требуется; статус меняется сразу.
4. **Изменение уже назначенного статуса:** разрешено в любой момент. Пользователь может вернуться кнопкой «Назад» к товару и изменить выбранный статус.
5. **Кнопка «Вперёд» на последнем товаре:** показать сообщение о завершении списка.
6. **Кнопка «Назад» на первом товаре:** заблокирована.
7. **Перелистывание свайпами:** не поддерживается; используются только кнопки «Назад» и «Вперёд».
8. **Отображение архивных товаров:** отдельный экран «Архив».
9. **Товар стал архивным в МойСклад:** локальный статус актуальности сбрасывается в «Нераспределённые».
10. **Архивный товар разархивирован в МойСклад:** при возвращении в обычный каталог показать пользователю запрос, какой статус назначить.


### Ответы на анкету № 5 — Журнал склада и Менеджер API

1. **Связь записей и задач:** поддерживать все варианты связей в зависимости от бизнес-операции: одна запись журнала может создавать одну или несколько задач API; несколько записей могут при необходимости объединяться в одну задачу.
2. **Момент фиксации в Журнале склада:** фиксировать оба этапа — создание намерения выполнить операцию и результат её локального сохранения.
3. **Разделение очередей:** создавать отдельные логические очереди по мере появления новых бизнес-логик.
4. **Порядок и параллельность выполнения:** базовое требование — строго последовательное выполнение задач в одной общей очереди. Безопасность важнее скорости: параллельность допустима только если будет доказано, что она не нарушает целостность, порядок и зависимости операций; иначе выполнять по одной задаче. Дополнительно нужен аварийный механизм остановки/разблокировки: если задача зависла в состоянии отправки и блокирует очередь, пользователь или система должны иметь возможность остановить зависшую обработку и вернуть Менеджер API в управляемое состояние. Точные условия срабатывания и восстановления требуют уточнения.
5. **Порядок задач:** FIFO — строго по времени поступления.
6. **Состояния и детализация:** краткое состояние показывать в общем списке задач; при открытии конкретной задачи показывать подробную историю переходов, попыток, ответов API и причин ошибок.
7. **Повторы:** временные ошибки повторять автоматически ограниченное разумное число раз; ошибки, не относящиеся к временным, оставлять для ручного рассмотрения. Точное число попыток и интервалы повторов определить в техническом проектировании.
8. **Реакция на ошибки:** обычную ошибку отдельной задачи изолировать — отложить эту задачу и продолжить очередь. Если проблема связана с доступностью API/соединения, приостановить все очереди до восстановления связи.
9. **Перезапуск приложения:** восстановить сохранённое состояние очередей и задач, но перед продолжением обработки запросить подтверждение пользователя.
10. **Управление задачами:** предоставить просмотр, ручной повтор задач с ошибками, отмену ожидающих задач, приостановку и возобновление очередей, а также подробности запросов/ответов API, идентификаторы и историю попыток.

### Архитектурные уточнения по анкете № 5

- Логические очереди разделяются по бизнес-логикам, но порядок отправки по умолчанию централизован: одна общая последовательная FIFO-обработка. Не следует автоматически трактовать наличие нескольких логических очередей как разрешение на параллельные HTTP-запросы.
- Приоритет безопасности и целостности выше производительности. Возможность параллельной обработки может рассматриваться только после анализа зависимостей и гарантий безопасности; до такого подтверждения действует последовательная обработка.
- Аварийная остановка нужна для восстановления после зависшей задачи, которая остаётся в состоянии отправки и блокирует дальнейшую работу. Таймаут обнаружения зависания, полномочия автоматического watchdog и последствия ручной остановки должны быть отдельно спроектированы.
- Ошибка отдельной задачи не должна блокировать остальные задачи. Исключение — общая недоступность API или соединения: в этом случае все очереди приостанавливаются до восстановления связи.
- При запуске приложения сохранённые задачи не должны самопроизвольно продолжать отправку: сначала требуется подтверждение пользователя.
- Детальные запросы и ответы API должны проходить безопасную фильтрацию секретов: токены и иные учётные данные не должны попадать в журналируемые данные.



### Ответы на пересмотренную анкету № 6 — локальная база и сохранность данных

1. **Организация локального хранения:** окончательный вариант не выбран. Пользователь спрашивает, будет ли надёжнее использовать отдельные базы данных для подсистем, и отмечает, что пока не имеет достаточного опыта в проектировании БД. Решение отложено до технического сравнения вариантов с объяснением преимуществ, рисков и последствий для транзакций и восстановления.
2. **Срок хранения Журнала склада:** ориентировочно один месяц на текущем этапе. Срок предварительный («пока что»), не считать окончательной политикой удаления до уточнения архивирования и очистки.
3. **Завершённые задачи Менеджера API:** хранить в течение настраиваемого срока.
4. **Удаление записей Журнала:** разрешить пользователю удалять записи с подтверждением.
5. **Состав данных операции:** сохранять ID, ссылку на локальную сущность и снимок ключевых полей; состав снимка зависит от типа операции.
6. **Согласованность операции и записи Журнала:** создавать их одной транзакцией — либо сохраняются оба, либо ни один.
7. **Резервное копирование:** нужны автоматические и ручные резервные копии.
8. **Повреждение локальной базы:** остановить работу с данными и запросить решение пользователя; автоматическое восстановление или откат без его решения не выполнять.
9. **Экспорт:** поддержать CSV и JSON с выбором раздела и периода.
10. **Удаление API-токена:** сохранять локальный каталог и Журнал склада, но очищать ожидающие API-задачи.

### Архитектурные уточнения по анкете № 6

- Вопрос о количестве физических баз данных остаётся открытым. Не считать отдельные базы автоматически более надёжными: необходимо сравнить их с одной базой, логически разделённой на независимые модули/таблицы. При сравнении особенно учитывать атомарную транзакцию между бизнес-операцией и записью Журнала, резервирование, миграции, восстановление и риск частичного рассогласования нескольких хранилищ.
- Предварительный срок хранения записей Журнала — один месяц. До реализации необходимо определить, означает ли это автоматическое удаление, архивирование или настройку срока хранения; само по себе указание срока не разрешает безвозвратное удаление.
- Удаление токена не должно удалять локальный каталог и историю Журнала. Ожидающие API-задачи очищаются согласно ответу пользователя; правила для уже выполнявшихся и завершённых задач требуют технически безопасного определения и фиксации результата очистки.

### Ответы на анкету № 7 — создание складских операций

1. **Первая бизнес-операция:** пока не выбрана. До выбора и реализации отдельных складских операций в разделе «Дополнительные действия» должны появиться и другие самостоятельные справочники/разделы: «Склады и места хранения», а также «Организации и способ оплаты». «Актуальные товары МойСклад» — не единственный пункт этого раздела.
2. **Выбор товаров для операций:** только из локального каталога «Актуальные товары». Операции не должны подменять локальный каталог прямым поиском по МойСклад.
3. **Черновики:** автоматически сохранять незавершённую операцию по мере заполнения.
4. **Редактирование после локального сохранения:** разрешить свободное редактирование операции до её отправки в МойСклад.
5. **Момент создания операции и записи в Журнале:** операция считается созданной и фиксируется в Журнале после нажатия пользователем «Сохранить» или «Создать». Автосохранение черновика само по себе не означает создание завершённой операции для Журнала.
6. **Работа без интернета:** разрешить полностью создавать и сохранять операции офлайн; отправка в МойСклад выполняется позднее, когда связь доступна.
7. **Повторяющиеся товары в одной операции:** каждое добавление товара оформлять отдельной строкой, не объединять автоматически одинаковые позиции.

- **Склады и места хранения:** показывать как единую иерархию, где места хранения принадлежат соответствующему складу. Не смешивать места хранения разных складов в плоский список без указания родительского склада.

Поиск запускается после ввода пользователем первых символов и находит совпадения по части наименования (пример: ввод «гло» позволяет найти «ООО Глобал Фуд»). Пользователь уточнил, что такой принцип поиска должен применяться ко всем поискам в приложении: ввод части слова, показ результатов после начала ввода, без предварительного вывода полного списка.
- **Получение и локальное хранение поставщиков:** каталог поставщиков загружается из МойСклад при поиске; поставщики, с которыми пользователь уже работал/которых сохранил, остаются в локальной базе. Для сохранённого поставщика обязательно хранить как минимум наименование, ID МойСклад и номер телефона. Локально связанный способ оплаты и статус актуальности также принадлежат Lerua Zakup.

Это не отменяет уточнённого сценария поиска поставщиков с загрузкой результатов по запросу; конкретное согласование фоновой полной синхронизации поставщиков и поисковой загрузки следует описать в технической спецификации.
- **Единая локальная база:** пользователь выбрал одну SQLite-базу с логическим разделением на таблицы и модули. При проектировании сохранить транзакционность связанных сущностей (операция и запись Журнала), независимость модулей на уровне архитектуры, миграции и единый механизм резервного копирования/восстановления.
- **Редактирование операций:** политика определяется типом операции. Для каждого вида операции необходимо явно определить допустимые изменения на стадиях «Подготовлена», «В очереди», «Отправляется» и при неопределённом результате.

Не показывать полный каталог до ввода запроса. Минимальную длину запроса, задержку перед сетевым поиском и поведение при пустом запросе определить в техническом проектировании.
- **Открытыми остаются:** конкретный экранный способ размещения организаций и способа оплаты; является ли «организация» в интерфейсе именно справочником поставщиков или включает другие типы контрагентов; точная политика синхронизации полного каталога поставщиков и поиска по API; минимальная длина/задержка поиска; набор доступных способов оплаты и источник их справочника; отдельные правила редактирования по каждому виду складской операции.

- **Очистка Журнала:** автоматическое удаление просроченных записей допускается только после успешного резервного копирования. Если копия не создана, очистку не выполнять. Настраиваемый срок хранения и начальное значение один месяц остаются согласованными по анкете № 9.
- **Открытые вопросы:** как именно выбирать организацию/способ оплаты, если у поставщика может быть несколько доступных организаций; что показывать, если ни одной организации или ни одному способу оплаты не назначено значение; допускается ли один способ оплаты для нескольких организаций; требуется ли отдельный выбор организации при подготовке конкретной операции. Эти правила следует уточнить до проектирования формы бизнес-операции.


### Ответы на анкету № 11 — привязка поставщиков, организаций и способы оплаты; надёжность Менеджера API

1. **Как определяется организация и способ оплаты при работе с поставщиком:** пользователь сначала назначает поставщику статус «Актуальный», затем открывает карточку этого поставщика и выбирает способ оплаты. Выбор способа оплаты связан с организацией МойСклад; именно эта настройка должна определять организацию, которая будет указываться в API-запросах будущих бизнес-операций с данным поставщиком. Пользователь не выбирает организацию и способ оплаты заново при каждой операции. Это уточняет прежнее описание анкеты № 10, в котором механизм определения организации при выборе поставщика оставался открытым.
2. **Повторное использование способа оплаты:** один и тот же способ оплаты нельзя назначить нескольким организациям.
3. **Количество способов оплаты у организации:** каждой организации можно назначить только один способ оплаты.
4. **Организация без способа оплаты:** предупреждать пользователя и предлагать сначала назначить способ оплаты. Не считать такую настройку корректно подготовленной для операции, которой требуется эта связка.
5. **Сохранение в складской операции:** сохранять ID организации и способ оплаты непосредственно в операции. Сохранять значения, действовавшие на момент создания операции, чтобы последующее изменение назначения в настройках не меняло ранее созданные операции и не вызывало каскадного изменения их реквизитов.
6. **Автоматические повторы временных ошибок API:** выполнять три попытки всего.
7. **Зависшая задача в состоянии «Отправляется»:** считать задачу застрявшей через пять минут и требующей аварийного вмешательства.

### Архитектурные уточнения по анкете № 11

- **Связь поставщика с организацией и способом оплаты:** уточнённый пользовательский сценарий — сначала поставщик переводится в статус «Актуальный», затем в его карточке выбирается способ оплаты. Выбранный способ оплаты однозначно связан с организацией МойСклад; по этой настройке система определяет организацию для API-запросов по будущим операциям с поставщиком. В интерфейсе не следует требовать повторного выбора организации для каждой операции, если только отдельный тип бизнес-процесса впоследствии не потребует специального исключения.
- **Кардинальность назначения:** связь способа оплаты с организацией — один к одному в обе стороны в рамках назначений: у одной организации не более одного способа оплаты; один способ оплаты не может быть назначен более чем одной организации. Не назначенный способ оплаты может оставаться в локальном справочнике свободным.
- **Отсутствующее назначение:** если для организации, необходимой поставщику, способ оплаты не назначен, пользователь получает предупреждение с предложением выполнить настройку до продолжения соответствующей операции.
- **Исторический снимок реквизитов:** при создании складской операции сохранять как минимум ID организации и выбранный способ оплаты в составе самой операции. Это неизменяемые для уже созданной операции значения на момент её создания; изменение текущих назначений в карточках поставщиков/организаций влияет только на новые операции. Точный состав снимка (например, сохранять ли дополнительно отображаемые названия) определить в технической спецификации, не подменяя сохранение ID.
- **Повторы API:** для временных ошибок — не более трёх попыток всего, включая первоначальную отправку. Неопределённый результат и ошибки, не классифицированные как временные, не должны автоматически повторяться; ранее согласованные правила ручной проверки и изоляции ошибочной задачи сохраняются.
- **Watchdog Менеджера API:** состояние «Отправляется» дольше пяти минут считается зависшим и должно запускать предусмотренный механизм аварийного вмешательства/разблокировки. Это не разрешает автоматически повторять запрос: сначала требуется безопасно установить, мог ли МойСклад принять операцию, и сохранить неопределённый результат, если подтверждение невозможно. Детали watchdog, безопасной остановки и восстановления очереди определить в техническом проектировании.
- **Приоритет решений:** ответы анкеты № 11 уточняют открытые вопросы анкеты № 10 о выборе организации и способа оплаты, повторном использовании способов оплаты и поведении при отсутствии назначения. Они также конкретизируют ранее открытые параметры повторов и аварийного контроля Менеджера API.


### Уточнение пользователя после анкеты № 11 — склады и локальные места хранения

- **Склады МойСклад** являются внешним справочником: Lerua Zakup запрашивает их через API, сохраняет локальные записи и обновляет эти записи при последующей синхронизации. Для каждого склада обязательно хранится его стабильный ID МойСклад; по нему локальная запись сопоставляется с внешней сущностью.
- **Места хранения** не являются сущностями МойСклад и не являются API-задачами. Пользователь самостоятельно создаёт локальные места хранения внутри конкретного склада. Они существуют только в Lerua Zakup и предназначены для будущей внутренней организации и распределения товаров.
- Локальное место хранения связывается с локальной записью склада через внутренний ID склада; сама запись склада содержит внешний ID МойСклад. Не отправлять создание, изменение или удаление локальных мест хранения в МойСклад.
- Подробные правила внутреннего распределения товаров по местам хранения отложены на последующий этап. На текущем этапе необходимо заложить корректное разделение внешнего справочника складов и локальной иерархии мест хранения, не проектируя преждевременно алгоритмы размещения товаров.
- Запросы и обновление справочника складов относятся к API-интеграции и выполняются централизованно через Менеджер API. Локальные CRUD-действия над местами хранения выполняются без постановки API-задач.
